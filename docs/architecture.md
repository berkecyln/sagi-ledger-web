# Sagi Architecture

## What it is

A personal income and expense tracker organised by month. The frontend is a React app on Vercel, the data lives in a self hosted PocketBase server. Every user's data is fully separate.

```
Browser (sagiledger.com)
  components
    → store (Zustand)       updates the screen at once
    → src/api/              the only code that talks to the server
    → PocketBase SDK
          │ HTTPS
          ▼
  api.sagiledger.com        PocketBase, SQLite
```

## Data model

One `Transaction` shape is used everywhere in the app (`src/types.ts`):

```ts
{
  id: string            // 15 characters, generated by the app
  type: 'INCOME' | 'EXPENSE'
  amount: number        // integer cents, formatted only for display
  description: string   // category label, e.g. "Rent"
  account: string       // bank name, e.g. "TEB"
  date: string          // "YYYY-MM-DD", or a day number "15" for template items
}
```

On the server the data is split into four collections, each row owned by a user:

| Collection | Holds |
|---|---|
| `accounts` | name, colour and base balance per bank |
| `descriptions` | the suggestion labels, per type |
| `transactions` | every entered transaction |
| `template_items` | the recurring items |

A transaction's `account` is a relation to `accounts` on the server and a plain name in the app. `src/api/accounts.ts` maps between the two.

## State (`src/store.ts`)

| Field | Notes |
|---|---|
| `months` | transactions grouped by `YYYY-MM`, derived from `date` |
| `template` | recurring items |
| `accountColors` | account name → hex colour, also the list of known accounts |
| `baseAccountBalances` | account name → starting balance in cents |
| `descriptions` | suggestion labels, one list per type |
| `activeMonthKey` | the month on screen, starts at the current month |
| `status`, `error` | loading state of the first fetch |
| `writeError` | last failed write, shown by `ErrorBanner` |
| `applying` | progress while a template is applied |

Nothing is stored in the browser. After sign in `AuthGate` calls `loadAll()` once and the store is filled from the server. Signing out clears it.

## Writes

Every action updates the store first, then writes to the server:

- **Optimistic:** the screen changes at once.
- **Rollback:** if the write fails, only the changed part is restored and `ErrorBanner` shows the reason. A failed template apply reloads everything from the server instead, as part of the month may already be written.
- **Throttle:** writes are queued at 15 per 5 seconds, under the server limit of 20. Applying a large template shows a progress bar under the MonthBar.
- **Unsaved guard:** `UnsavedGuard` warns before closing the tab while writes are still pending.

Two devices editing the same row is last write wins.

## Months and template

Months start empty. **Apply Template** in the MonthBar replaces the active month's transactions with a copy of the template. A template item's day is placed in the month and clamped to its length, so day 31 lands on the 28th in February.

Dashboard, Analytics and Ledger read and edit only the active month. A transaction is always stored in the month of its date, so a new or edited row dated in another month moves there.

## Accounts

An account exists once any transaction or template item names it, or when it is added in the base balance settings. Each gets a colour from `src/utils/colors.ts` on first use, shown through `AccountTag` wherever an account name appears.

An account can only be deleted while nothing uses it (`isAccountInUse`). Deleting a bank never deletes transactions.

## Description labels

Labels are a user owned list per type, so income and expense suggestions never mix. It is the one stored value that is not derived from transactions.

- Typing a new label does not save it. Only the `Create "X"` row does.
- Removing a label removes the suggestion only. Transactions keep their text.
- The Ledger's description filter is derived from the actual transactions.

## Sign in

`AuthGate` shows `AuthScreen` when there is no session. Sign up needs an invite code, typed by the person signing up. Sessions last 90 days, so the password is typed about once per device.

## App shell

```
AuthGate
  Layout
    Header              logo, page links, theme toggle, sign out
    MonthBar            ◀ September 2026 ▶, Apply Template
    main → page
    TotalBalancesFooter desktop only
    AddActionButtons    phones, Dashboard only
    ErrorBanner
    UnsavedGuard
```

Desktop fills the screen and pages scroll inside. Phones scroll the whole page. The app installs to the home screen through `public/manifest.webmanifest`.

## Local development

`npm run dev` never touches production. It starts a local PocketBase in Docker on `127.0.0.1:8090` and the app reads it through `.env.development`.

| Path | Holds |
|---|---|
| `pocketbase/Dockerfile` | PocketBase at the same version as production, checksum verified |
| `pocketbase/pb_schema.json` | Production schema export, test invite code `test-invite-code` |
| `pocketbase/pb_migrations/` | Imports the schema and a superuser `test@sagi.local` on first start |
| `pocketbase/pb.sh` | `up`, `down`, `reset` for the dev container, `test-up`, `test-down` for the test container |

The data is kept in a Docker volume between runs. `npm run seed` deletes it, starts fresh and creates the demo user `test` with password `test1234`. After a schema change in production, export the collections again into both schema files and run `npm run seed`.

## Tests

| Command | Runs |
|---|---|
| `npm test` | `tests/unit`, offline, store and api layer mocked |
| `npm run test:live` | `tests/live` against a fresh PocketBase on `127.0.0.1:8091`, started before and removed after the run |

The live tests cover the api layer round trip, the server rules for money, dates, labels and accounts, and the isolation between two users. Nothing runs against production.
